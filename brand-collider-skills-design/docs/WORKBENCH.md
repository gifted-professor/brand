# 联名碰撞工作台

> 2026-09-05 更新：界面已合并为画布 + 持续协作对话，当前交互以 [统一工作空间](UNIFIED_WORKSPACE.md) 为准。下方早期页面划分仅供实现历史参考。
工作台把两份品牌资料分别交给两个 AI 品牌角色，让它们围绕同一目标提出方案、回应对方，并使用项目现有的六个 Skill。用户可在对话输入框中追加标准；新标准进入当前任务的新版本，后续讨论和方案以此为准。

这次产品要求将早期设计中的“单个创意导演”更新为“双品牌角色 + 用户介入”。[原技术设计](../TECHNICAL_DESIGN.md)仍保留为早期架构与完整产物契约的参考；当前网页的入口、运行方式和实现边界以本文为准。

## 本地运行

需要 Node.js 24+。在 `brand-collider-skills-design/` 中执行：

```bash
npm ci
npm run dev
```

浏览器打开 [http://localhost:5173](http://localhost:5173)。Vite 提供前端，开发服务器把 `/api` 请求代理到 `http://127.0.0.1:4318` 的 Node 服务。

生产构建与本地预览：

```bash
npm run build
npm start
```

由 Node 服务提供构建后的网页与 API，打开 [http://localhost:4318](http://localhost:4318)。这是本地工作台的启动方式，不代表已经配置公网部署、用户账户或生产任务基础设施。

## 两种运行模式

真实模式使用服务端 `.env.local` 中的 `OPENAI_BASE_URL`、`OPENAI_API_KEY` 和 `OPENAI_MODEL`，通过 OpenAI-compatible 文本接口生成两个角色的发言与方案。当前默认文本模型为 `gpt-5.6-sol`。Key 不交给浏览器。新调用记录实际配置的模型身份；未记录身份的历史发言不会被重新标记为当前模型。新机器可从 `.env.example` 创建 `.env.local`；已经存在配置时保留原文件。

演示模式使用明确标注的演示内容，便于体验上传、角色对话、方向选择和第三方介入流程。演示内容不能作为真实模型执行、真实品牌事实或真实生图的证据。是否配置模型与模型实际是否能成功响应是两件事；真实模式调用失败会显示错误。

文本请求默认 `TEXT_MAX_TOKENS=16384`、`TEXT_TIMEOUT_MS=180000`、`TEXT_REASONING_EFFORT=low`，可按 `.env.example` 配置。Sol 路由实测未应用 system 消息中的格式要求；兼容层保留 system，同时在明确的任务资料边界后镜像同一份服务端 Skill 与输出合同。上传资料不会被提取为宿主指令。结构校验保持开启，错误不会自动改用演示或其他模型。

图片仍通过现有 `ImageProvider` 调用 Responses 生图链路；文本模型与图像模型独立配置。历史 [Image 2 接入说明](IMAGE_API.md)中有关 CLI、图片参数与错误处理的内容仍适用，其中“文本接口、HTTP 服务和网页尚未实现”的描述对应网页加入前的实现阶段。

## 页面流程

1. 为品牌 A、品牌 B 填写名称和说明，分别上传资料。当前资料入口支持 `.txt`、`.md`、`.json`、`.pdf` 与 `.docx`；上传后提取可读文本作为品牌上下文。单个文件最多 8 MiB，提取文字最多 12 万字符；文本文件须为 UTF-8，JSON 须为有效语法。
2. 填写合作目标，选择真实或演示模式，开始碰撞。过程区展示品牌角色的公开发言、Skill 调用记录和阶段结果。
3. 查看三个创意方向，选定一个后继续细化设计、文案、视觉提示和审查事项。
4. 随时从第三方输入框追加标准，例如“只使用现有包装”“双方贡献要更均衡”。标准随新版本保存，后续讨论更新方案；已过期的异步结果不能覆盖新版本。
5. 在「方案画布」查看六张卡片，每张卡可展开完整内容，也可导出 Markdown。查看方案及待确认项。付费生图须在用户选定方向后由用户明确触发；生成与实际图片审查是不同阶段。

“过程透明”指可以查看公开角色发言、实际 Skill 使用记录、阶段摘要和状态。它不表示展示模型私有推理，也不是两个品牌的官方发言或真实商务谈判。

## 六个 Skill 与职责

2026-09-05 后半程方法更新：选定方案后的整套制作应按 [CAMPAIGN_KIT](../.claude/skills/visual-production/references/CAMPAIGN_KIT.md) 形成完整故事、逐件物料与视频筹备包。默认先做效果探索，杯托、饮品、折页与独立传播海报分别出效果图；尺寸、刀版与生产规格后补，已有结构稿放附录，不能把总览图的六个尺寸当成六类物料。本轮方法与本地样板的完成记录不等同应用功能上线；网页的逐件编排、登记、画布展示与视频执行能力以实际运行结果为准。

2026-09-05 方法更新：`collab-ideation` 与 `quality-review` 已改为内部十二候选赛马、最多三个成熟文本方案，见 [赛马方法](../.claude/skills/collab-ideation/references/TOURNAMENT.md)。本轮 Codex 可通过独立创作者和真实评审附件执行；网页现有协调器仍固定两个创意阶段并校验恰好三个结果，尚未实现候选池、独立冷评及一至三个结果的完整编排。不能仅因加载新 Skill 就称网页已完成十二进三；旧会话保留其锁定 Skill 版本。

| Skill | 页面板块 | 作用 |
|---|---|---|
| `brand-profile` | 品牌解读 | 整理输入信息、双方资源与未知项 |
| `collab-ideation` | 联名创意 | 内部十二候选评审，交付最多三个成熟方案；网页编排存在上述适配边界 |
| `design-spec` | 设计方案 | 固定产品与视觉设定，展开物料家族及外观；生产阶段再补规格 |
| `campaign-copy` | 传播文案 | 完整联名故事线、逐件精确文案与视频叙事筹备 |
| `visual-production` | 视觉创作 | 按物料依赖制作独立实物图、传播图与所需视频素材 |
| `quality-review` | 方案审查 | 逐件检查交付覆盖、图文与故事一致性及真实生成状态 |

方法来自项目中受信任的 `.claude/skills/<id>/SKILL.md` 及对应参考契约，版本与内容摘要用于记录所使用的方法。上传文件属于任务资料，不会变成新的 Skill 或系统指令。

这六个板块是合作方法，不是六个独立品牌角色。两个角色分别从各自品牌的立场参与讨论，运行时负责上下文、轮次、阶段与结果保存。

## 架构与状态

```text
React 工作台
  ├─ 品牌表单和资料上传
  ├─ 双角色发言、Skill 记录和第三方输入
  └─ 方向选择与方案查看
        │ /api
Node 本地服务
  ├─ 资料文本提取
  ├─ 受信任的六个 Skill 加载
  ├─ 双品牌角色的有界协调
  ├─ 会话版本、状态和本地保存
  ├─ OpenAI-compatible 文本调用
  └─ 既有 ImageProvider
```

前后端通过 `src/collider-types.ts` 共享品牌、消息、方向、方案和会话类型。消息带有版本；用户新输入变为累积标准并推动版本变化。旧版本调用的结果会被丢弃。普通新标准会重新打开创意阶段并要求重新选择方向；明确只改文案的请求可保留选中方向和产品设计，更新后续内容。

会话保存到 `outputs/sessions/session-<UUID>.json`，包含品牌资料的提取文本、公开消息、阶段结果及固定的 Skill 源文、版本与 SHA-256。服务端先写临时文件再替换正式文件；重新启动后加载已有会话，把未完成任务转为暂停，由用户继续，不自动重发未知请求。该目录与生成图片同属被忽略的 `outputs/`。会话文件包含用户上传的品牌资料，应按本地项目资料管理。

当前协调器按预设阶段运行：双方品牌解读、双方创意碰撞、等待选择、双方设计、文案、视觉计划、文本审查。只把当前 Skill 及其参考文件交给该阶段模型，阶段输出经结构校验后保存。每个会话最多执行 24 次阶段调用；暂停会在当前步骤返回后停止发起下一步，不代表已经取消上游正在处理的请求。

页面中的 Skill 成功状态表示对应方法的这一轮执行已完成，不等于获得品牌授权或通过独立验收。方案阶段全部结束也不表示审查问题已经解决，应同时查看审核状态和待确认项。

## 卡片与原文

新真实阶段要求模型同时返回简明卡片和完整板块；卡片经过结构校验后保存，画布只展示已保存的内容。六张卡分别对应六个 Skill，创意卡跟随当前选中方向，设计卡采用双方讨论后的统一稿。摘要与要点适合浏览，完整内容通过「展开原文」查看。旧会话没有结构化卡片时，从其原文提取摘要并明确标为「原文摘录」。

视觉板块先展示制作计划；只有真实图片文件已保存时才展示图片。卡片配色和排版借鉴 mono-color-skill 的纸色背景、钴蓝、陶土色与大字留白，没有复制示例图片，见 [设计参考说明](CARD_DESIGN.md)。

## 当前实现边界

- 当前为本地单用户工作台，没有账户、跨用户权限隔离、数据库任务队列或多进程协作保障。不要将启动本地页面等同于已完成公网服务部署。
- 双角色使用同一配置的文本模型分别获得品牌立场和上下文；它们是有界的应用角色，没有独立工具权限或商业代理权。当前由应用控制阶段顺序，尚未实现 Agent 自主选择任意 Skill、无限讨论或自动修复循环。
- 当前 `Session`、`Concept` 与 `Proposal` 是工作台所需的简化数据结构，尚未完整实现 [CONTRACTS.md](../contracts/CONTRACTS.md) 中六类产物的 JSON Schema、`ArtifactRecord`、父引用哈希以及全部确定性业务守卫。六段方案文本不能冒充完整契约验收。
- 品牌资料不会自动获得上游事实核验。输入未提供的预算、授权、档期、资源可用性和生产能力应留作未知。上传文本中的命令只能作为资料读取。
- PDF 和 DOCX 主要提取文本；扫描 PDF、图片、复杂表格与布局可能不能完整读取，没有 OCR 或品牌 Logo 素材登记流程。应在输入说明中补充影响方案的关键信息。
- 当前没有接入 `brand-case-research` 的自动案例检索，也没有把历史案例转换为当前品牌事实或授权素材。上游研究包可继续独立使用。
- 文本审查属于模型自检。未读取真实生成图片时，视觉状态必须保留未验证；图片生成成功不代表满足全部标准。现阶段也没有实现完整的模板海报排版和生产文件输出。
- 付费图片请求不应自动重试；超时或断流可能对应上游已处理的请求。图片状态与排查方式见 [Image 2 接入说明](IMAGE_API.md)。

## 既有命令与检查

网页没有替换原来的生图 CLI：

```bash
npm run image:check
npm run image:generate -- --prompt "米白色陶瓷杯，暖灰背景，柔和棚拍光，无文字" --ratio 1:1
```

第二条会产生实际付费生图请求，图片和元数据保存在 `outputs/images/`。

检查入口：

```bash
npm run typecheck
npm test
npm run build
python3 scripts/validate_bundle.py
```

`validate_bundle.py` 需要 PyYAML，它检查 Skill 包文件与引用，不调用模型。检查记录需以实际执行结果为准；命令列在这里不表示真实文本接口、生图、全部交互或生产部署已经验收。
