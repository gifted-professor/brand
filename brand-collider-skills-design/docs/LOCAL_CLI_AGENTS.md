# 本地 CLI Agent 执行

网页实时协作支持本地 Codex CLI 与 Grok CLI，当前本机按用户要求切换为 Grok 试用。调用链为：网页 → 本地 Node 宿主派发 → 专业及素材 Agent 的 CLI 子进程 → 结构化结果与真实来源校验 → 逐件参考绑定 → 最多四并发图像 provider → CLI 实际附图审查 → 对话与无限画布。主控交接由宿主直接生成；模型计算仍由各 CLI 登录所连接的模型服务完成，不是在本机离线推理。

## Agent 身份与生命周期

| Agent ID | 职责 | 会话范围 |
| --- | --- | --- |
| `orchestrator`（宿主角色） | 按阶段定义记录版本、输入依赖及交接目标 | 无新 CLI 会话；历史执行记录保留 |
| `research-a`、`research-b` | 并行独立研究双方品牌资料 | 各自独立，两份有效研究汇合后才进入创意 |
| `creative-a`、`creative-b` | 根据品牌视角完成创意、设计、文案及视觉计划 | 每次阶段执行使用新 `contextId`，不跨阶段恢复历史 |
| `review-a` | 接收完整有效成果，进行同模型文本审查 | 独立于研究和创作 |
| `media-reference-discovery-<hash>` | 分别为双方发现真实公开来源页与图片地址 | 按任务输入身份与简报版本隔离 |
| `media-reference-inspection-<hash>` | 实际接收原图并核对来源、主体和版本 | 每项素材的独立核对任务 |
| `media-reference-binding-<hash>` | 为当前物料绑定已登记参考与依赖 | 按当前计划隔离 |
| `media-pre-render-review-<hash>` | 审查已就绪物料的设计、提示词与绑定 | 独立出图前任务 |
| `media-image-review-<hash>` | 实际接收参考和生成结果，逐件审查 | 按实际物料与文件隔离 |


每次专业或素材 Agent 激活启动一个真实 CLI 子进程，完成后退出。主流程保留五个专业身份，每次阶段执行使用新的 `contextId`；无修复的完整九步建立九个主阶段 CLI 会话。同阶段当前提交的一次自动修复可复用其成功保存的会话 ID：Codex 使用 `codex exec resume`，Grok 使用 `--resume`。后续阶段或手动重试使用新上下文，不恢复同一创作身份的历史任务；不会使用最近任意会话或借用当前开发任务的会话。主控角色不启动交接进程，素材任务仍按任务输入身份和简报版本隔离。

主控由应用代码维护允许派发的阶段、采用方向及提交格式，并直接生成交接记录，不额外请求模型重述下一步。九个主阶段保留原展示顺序，第 1–2 步同时启动，B 方研究不以 A 方研究为输入；第 3 步等待两份有效研究均提交，之后创意、设计、文案、视觉与审查按依赖执行。自动路径的双方初始素材支线与文字研究并行，第 3 步还汇合采集与实际看图结果或局部缺口，使创意使用真实素材依据。第六步统一设计提交后即补采，并与文案及逐件提示词制作并行；第八步汇合后按物料依赖调度真实生成和图像审查。

简报版本变化后启动新版本的 Agent 会话。已保留的有效成果通过共同简报显式传入，新旧会话不混用。暂停立即中止正在执行的 CLI，未完成阶段不提交；继续时用新阶段上下文重试，保留已完成的另一方研究。正常关闭服务会停止进程组并保存中断状态。异常重启不自动重试未确认请求。

## 连续推进与有限修复

品牌名称即可启动；品类、描述、附件和目标为选填，未填目标使用“探索双方品牌的联名方案”。资料数量影响证据密度，不影响是否进入下一阶段。研究优先使用实际可用的公开线索；仍未知的内容采用明确、可替换的工作假设，预算、授权、生产或渠道条件列为落地待确认，不把“补齐资料”作为概念推进门槛。

新会话默认 `autoAdvance: true`；实时网页开始协作同时明确传入 `autoProduce: true`，连续完成九个专业阶段：双方研究、创意提出与收敛、设计深化与统一、文案、视觉制作、审查。素材发现和实际看图从研究开始并行；创意提出前汇合初始采集与核对结果或缺口，缺来源不阻止文字创作。第八步在逐件提示词完成后按设计补采与绑定参考、检查就绪条件、默认生成 core 与 recommended 并逐件审查，optional 保留候选；第九步汇总实际证据。无 autoProduce 或为 false 的历史/API会话维持原视觉计划与单图入口。模型按推荐顺序提交概念，主控采用首项并记录 `selectionSource: "orchestrator"`，再继续后续工作；用户仍可调整方向或修改要求。API 显式传入 `autoAdvance: false` 时保留等待用户选择的分支，用户选择记录为 `selectionSource: "user"`。

无修复的完整基础文字流程为九次专业模型调用、八层阶段依赖，主控交接不增加模型调用。这个计数不含自动修复、素材发现、图片核对、参考绑定、出图前及逐件图片检查，也不含生图。单次专业提交遇到结构错误、临时 CLI 失败时最多自动局部修复一次。每个由用户发起的工作轮次最多 48 次 provider 调用、24 次阶段尝试，累计用量另行永久保留；两种限制分别约束模型请求和阶段推进，不按对话消息条数计数。资料不足不会消耗无休止的追问轮次。只有用户明确改用已有的另一方向或提交新的要求，才开始新轮次额度；首次选方向、重复选择、继续、暂停、自动修复和维护性重新研究均不重置。

上述 48 次是基础阶段调用额度。自动素材链独立按简报版本累计，最多 96 次真实 provider 调用；它不是额外图片数授权，真实生图仍只覆盖本轮选定清单。看图任务自身受控排队，与最多四个在途生成请求分别管理。任何一项就绪即可开始，释放一个生成槽就补下一个，不等满四项或整组结束；unknown 持续占槽直到核实终态，failed/unknown 不自动重发，审核需修订也不自动无限生图。


`blockedReason` 不能因资料稀少而终止已有有效交付：完整正文通过校验后，非空原因纳入 `pendingConfirmations` 继续。空正文、占位说明、缺少必要结构仍需修复，不能为走完流程凑造产物。自动修复后仍失败、用户暂停或达到调用限额时，保存真实进度与错误，保留已完成成果。

更新既有项目方法时，`intervene` 可传 `refreshResearch: true`：建立新简报版本，刷新当前 Skill 固定快照并重新研究；旧快照保存在 `pinHistory`，旧成果保持可追溯。普通修改继续遵循成果复用规则，不悄悄把历史研究改称已重新核验。

`intervene` 对整句纯继续指令记录同版本控制消息，并继续当前已授权流程。其他普通消息和混合修改意见仅记录讨论，不更改简报版本、标准、阶段成果、选中方向或在途制作；通知明确说明意见尚未应用。只有显式传入 `restartFrom: 1..9`，或整句输入“从第 N 步重新开始／重新执行／重做”，才从指定阶段建立修订；该阶段之前必须已完成，不能跳步。`refreshResearch: true` 是显式从第一步刷新研究的操作。旧测试与调用方需要明确提供重做起点，不能再依赖聊天内容自动使后续成果失效。

继续指令不更改 `autoProduce`，不调用历史会话的付费单图入口；正在生成的单图保持原请求。`autoAdvance: false` 且未选方向时仍等待选择，已完成会话保持完成；自动制作续跑可重新汇总最终审查，已完成设计和真实图像证据继续保留。

## 补采与生成验收的并行

宿主在 design-b 提交有效 MaterialPlan 后调用 `prefetchPlanReferences`，与 copy-a、visual-b 重叠。补采固定设计输入与计划哈希，不提前固定视觉提示词、绑定或付费批次；prepare 汇合该支线后按正式提示词绑定。相同计划共享一次在途工作，已完成补采不重复检索；暂停中止旧调用，续跑保留原图并补齐实际查看，版本改变隔离旧结果。

`runImageBatch` 的生成队列保持最多 4 槽，验图回调独立限流，默认 `reviewConcurrency: 2`（可用范围 1–4）。尚未开始的物料实际通过 referenceTasks 引用的共用图优先验收；普通排序 dependencies 不冒充图像依赖。验图不占生成槽，已经通过且输出哈希匹配才释放参考依赖；暂停只排空已开始操作，继续时复用成功图片，不重发已完成的付费请求。

### 明确失败的单物料恢复

`POST /api/sessions/:id/retry-media` 接收当前 `revision`、明确的 `materialIds` 和 `evidence`（重试依据）。会话与媒体必须已空闲；仅终态 failed、无图片且未验收的指定物料可登记一次新尝试。接口只登记，不直接生图；随后调用原 `/run` 才实际提交。普通继续不会重试失败请求，unknown 必须先取得外部结果证据并核实终态。

重试沿用同版已冻结的设计、提示词、参考与预检，保留成功图片；旧请求 ID、失败信息、实际参考哈希和重试依据进入 `retryHistory`，新尝试使用新请求 ID。只重新开放由该失败引起且依赖已经可用的下游项，再按实际图片及哈希验收放行。每物料同批最多一次显式重试；持续失败应修复具体原因，不能循环重新发图。简报变化、源文件变动、重复登记、运行中或已有产图的任务均拒绝。

图像请求的 `request.json` 保存有界的 `diagnostics.httpStatus` 与 `diagnostics.upstreamFailure` 分类，供区分实际服务错误；任意上游 message、提示词、鉴权内容和原始响应不进入这份诊断。旧记录没有的错误不能事后猜测补填。

### 实际图片的同设计质量纠正

`POST /api/sessions/:id/correct-media` 仅接收当前 `revision`、单个 `materialId`、`instruction`（落实既有要求的纠正指令）和 `evidence`（实际图像审阅依据）。只接受已暂停、无在途工作、当前设计与绑定已通过出图前检查，且真实产图的审查为 `needs_revision`、审查哈希与产图一致的物料。它用于纠正图片对既有要求的偏差；改变角色、产品、范围或设计仍走简报修订。每物料最多登记一次；已有产图的下游、未知请求、已通过的图片、重复登记及文件哈希变化均拒绝。

登记后保持同一简报版本、前八步成果、标准、方向、来源 ID、绑定与原预检结论。仅目标任务追加纠正指令，将旧图作为编辑参考（总参考数仍不超过四张），并以新的尝试身份等待执行。`correctionHistory` 单独保存原清单、任务、请求、图片、审查、文件与清单哈希及本次指令、依据和时间；原图不会变成官方身份依据。接口不调用模型或生图，随后 `/run` 从图像执行恢复，不重复采集、绑定或出图前检查。

新图必须重新附带真实参考并接受逐件看图检查；审查读取实际提交的完整提示词、本次纠正及原审查证据，确认新图的精确哈希通过后才放行依赖。若当前只有需纠正的实际图片，其余未完成项都仅等待这些图片通过，宿主暂停并保留 `review-a` 待完成，避免额外文字总审重复已知问题；存在其他已完成图片、未知请求或无关阻塞时保留通常的全案审查流程。

### 官方原件贴合与独立验图

用户明确选择将官方原 Logo 贴入既有图像后，可通过 `POST /api/sessions/:id/postprocess-media` 登记已经完成的本地后期结果。参数为当前 `revision`、`materialId`、`expectedOutputHash`（待处理原图哈希）、`sourceReferenceId`、`outputPath`、`processing: { tool, parameters }` 和 `evidence`。接口要求会话已暂停、无在途工作、当前版预检已通过，原付费图的真实审查为 `needs_revision`；可直接后期处理，不必先再生图一次。来源必须是当前绑定中已核验的官方身份原件，宿主重新核对源图与来源页哈希。输入仅允许当前 `media/vN/postprocess-staging` 内非符号链接的完整 PNG，尺寸与原图一致，每物料只登记一次。

宿主将新图复制到配置的图像目录，标记 `kind: local-postprocess`、`generationStatus: postprocessed`，不填写新模型或供应商请求身份。`postprocessHistory` 保存旧图片、请求、审查、官方源哈希、处理工具和参数、依据及新图哈希。登记本身不编辑像素、不调用模型；保持同版阶段成果、来源、清单、绑定及预检。随后 `/run` 复用现有队列，对实际新图重新验收，精确哈希通过后才继续依赖项。

若另有真实独立看图复核，可在制作空闲时使用现有本地 `recordImageBatchReview({ statePath, taskId, outputHash, status, evidence, reviewer })` 登记结论；它不是通用 HTTP 改判接口，也不替代实际查看图片。`outputHash` 必须匹配当前登记产物，函数再次核验文件；外部复核应在 `reviewer` 明确署名实际审阅者，在 `evidence` 写清原件对照、可见结果与局限。已有结论完整追加到 `reviewHistory`，包括原 CLI 的拒绝，不改写原 CLI 返回或冒称模型自行改判。通过只对该精确文件有效，也不代表品牌授权或生产认证；后续 `/run` 读取真实登记结果后才解除对应图像依赖。

## 每次请求的上下文

生图前局部纠正可使用 `POST /api/sessions/:id/amend-production-draft`，提交当前 `revision`、外部复核 `evidence` 和完整 `records`（恰好包含 design-b、copy-a、visual-b）。只接受已暂停、前八步完成、无任何付费请求或在途工作的草稿。保留方向与物料 ID、品类、优先级、依赖及交付范围；允许设计/文案/提示词、等长变体说明和合法 `aspectRatio` 的纠正。可选 `selectedConceptText` 仅接受 description、contributionB，用于同步修正当前概念卡的文字，不更改方向 ID 或标题。

修订建立新版本并保存 `productionDraftAmendments` 原文/新文审计，明确来源是外部复核，不改原模型消息。旧版核验原文件按哈希复制，原核验正文保留，纠正依据单独传递；不继承旧绑定、预检或图片审查。接口不生成图片，随后调用 `/run` 才重新绑定、预检和制作。已有任何付费请求时拒绝该接口，不能用改稿擦除失败或未知结果。

宿主保持原始 Skill 及共享参考正文完整加载、固定版本和内容哈希。本次压缩任务数据：两方研究各读自己的原始介绍和上传正文，对方只提供介绍和文件来源清单；后续保留品牌名及文件名、字符数、哈希，用两份通过结构校验的完整研究正文承接事实、用户声明、来源及未知项，不传重复原文或另外生成研究摘要。

下游 `currentArtifacts` 只包含两份完整研究及当前实际依赖：创意收敛增加创意初稿，设计统一增加设计深化，文案读取统一设计，视觉再读取文案，最终审查再读取视觉计划。每份记录保留 `basedOnRevision` 和 `pendingConfirmations`。当前目标、全部标准、所选概念、采用来源及最新 `artifactContext` 始终传入；参考快照不提升为指令，也不把保留的旧研究宣称为已经重新核实。

`materialPlan` 只在文案、视觉、审查请求中各传一次，最终审查再读取逐件 `materialVisuals` 与主图 `imagePrompt`。公开讨论仅保存在会话及画布，不再作为 `publicDialogue` / `lastPartnerMessage` 重复输入。前序阶段的素材上下文保留来源、哈希、核对结论与限制，最终审查额外接收每件物料完整的绑定、实际附图、生成及验收记录。完整存档继续保留，具体阶段映射见 [阶段交接](AGENT_WORKFLOW.md#按阶段提供上下文)。

独立阶段上下文避免同一创作身份通过 resume 隐式恢复前几步全文。自动修复仍可能包含该阶段已有历史，调用字符指标只反映新提示词，不含图片、Schema 和修复历史，不能作为服务端总上下文 token 计数。

## 服务稳定性与恢复

`npm run dev` 和 `npm run dev:api` 使用普通 Node 进程，后端不监听源码变化。前端仍可热更新；修改后端后，需要先结束或暂停现有任务，再手动重启服务。

服务先占用监听端口，再读取与修复保存的会话，防止第二实例在端口冲突前改写正在运行的项目。初始化及停止期间返回带 `service_starting` / `service_stopping` 的 JSON 503，凭据读取不阻塞事件循环。`outputs/runtime-events.jsonl` 记录服务进程、启动、停止及信号，不写品牌资料或密钥。

网页对读取请求的连接故障最多重试两次。提交请求绝不自动重发；响应丢失时，根据已有会话 ID 读取真实进度，并在核对完成前禁用重复提交。首次加载遇到服务启动期会保留原会话 URL 并继续恢复。CLI 或结果校验失败保留实际错误，不伪装成网页断线。

正常停止服务会在对话中明确记录原因，暂停正在执行的 Agent，保留已完成成果；恢复后由用户继续未完成步骤。宿主派发时，画布显示共同简报与交接记录；专业成果只有成功校验后才写入，不将派发记录展示成模型已经完成的分析。

本机为 Grok Build 1.0.13，当前默认模型实测为 `grok-4.6-build`。不设置 `GROK_CLI_MODEL` 时使用 CLI 默认模型；显式设置时才传入模型参数。普通文字角色通过 stdin 提供任务；真正看图的任务使用宿主生成的 ACP JSON 文件与 `--prompt-file`，每个 image 内容块携带真实 base64 图像和 MIME，避免命令行参数长度限制。两种路径均传入 `--verbatim`，不依赖模型调用文件工具读取提示词或图片。JSON Schema 用于约束公开结构化交付，CLI 包装回包中的 thought 不进入对话或公开文件。

品牌研究角色及 purpose=reference-discovery 的素材任务仅开放 `web_search` / `web_fetch`，同时以 `--allow WebSearch --allow WebFetch` 显式允许；最多六个 CLI 内部轮次。任务要求优先官方来源、最多两次查询与两次页面读取，保留 URL 与日期；查不到或读取失败时用明确假设交付。若提交失败，唯一一次自动纠正关闭新检索，要求直接用当前证据与明确假设完成正文；不会反复承诺稍后提交。视觉核对及其他非检索角色禁用工具与联网，最多三个内部轮次；视觉核对通过真实图片内容块完成，无需开放 read_file。所有角色均禁用子 Agent、项目扫描与任意本机执行；网页资料中的指令不能改变宿主任务。

项目、简报版本、Agent 及主阶段 `contextId` 分别隔离，Grok 与 Codex 使用不同的输出目录，不混用会话 ID。成功调用保存 Grok session ID，主阶段仅当前上下文的自动修复可使用 `--resume`；后续阶段或手动重试使用新上下文。单次 Grok 激活默认十分钟超时，CLI 内部轮次与应用阶段、provider 调用上限分别计数。默认自动采用推荐方向，不停在等待选择处，也不进行无休止的互相回复。

Grok 子进程使用项目专用 `GROK_HOME`，关闭 Claude/Cursor 的全局规则、Skill、MCP 和 hook 兼容加载，避免个人指令混入品牌任务。`GROK_AUTH_PATH` 仅引用现有认证文件，不读取或复制认证内容；专用 `collider` 沙箱继承 `strict`，额外允许现有认证目录读写，以支持 CLI 自己读取登录、锁文件及原子刷新。沙箱配置按 provider 一次初始化并原子发布，避免并行激活时读到被截断的配置。旧会话映射必须带 `isolationVersion: 1` 才能恢复，否则启动新的隔离会话。

Grok 结果诊断只保存白名单字段（结束类型、是否结构错误、会话身份是否匹配、是否存在结构化对象），不记录原始包装或私有思考。明显仅写“正在研究／稍后提交”的正文不计为成果，历史占位成果在显式刷新时撤销，保留原始执行记录。

## 文件与工作记录

`outputs/cli-agents/<session-id>/v<revision>/<agent-id>/` 保存该 Agent 的会话映射。每次调用在独立的 run ID 子目录保存任务快照、输出 Schema、最终 JSON 和执行元数据。共同简报、校验后的产物与决策仍由应用统一保存到原项目会话中。

Grok 对应记录在 `outputs/grok-agents/`。图像任务的隔离 run 目录另保存冻结原图、`attachments.json`，以及 Grok 真正发送的 `prompt.json`。宿主提供的图片必须是本地普通文件、哈希相符并能完整解码为静态 PNG/JPEG/WebP；适配器拒绝 URL 和最终路径符号链接。普通 CLI 最多接收 12 张、每张不超过 12 MiB、合计不超过 48 MiB；下游生图服务的参考数量/大小限制另行执行。

自动制作状态保存在会话输出目录下 `<session-id>/media/v<revision>/automation.json`，另有来源原件、批量清单及 `batch-state.json`。网页只接收登记素材的访问地址及来源、映射、哈希、生成与检查状态，不接收任意本地路径。原始素材、实际送入 provider 的参考图、CLI 审查附件与生成结果的哈希分别保留；模型观察和局限随物料保存，不能只靠文件存在或 request ID 判为通过。


消息的 `execution` 记录真实 `agentId`、run ID、PID、CLI 会话 ID、简报版本、开始/结束时间及执行状态。网页顶部显示本地 CLI；打开“工作记录”后可查看具体进程与会话。历史 API 消息不会补造 CLI 身份。

`execution.metrics` 按实际调用尝试记录 `attempt`、修复原因及可观察耗时：`inputChars` 是新文本提示词的 UTF-16 字符长度，不含图片、Schema 和恢复会话历史；`preparationMs` 是启动子进程前的本地准备；`processStartupMs` 是调用 spawn 到操作系统 spawn 事件；`firstStdoutMs` 是 spawn 到首个 stdout；`processDurationMs` 覆盖进程关闭（含中止等待），`totalDurationMs` 还包含准备与结果处理。首个 stdout 可能只是元数据，Grok 普通 JSON 回包也可能直到最后才整体输出；这些指标不能当作首 token 延迟，不能准确拆分模型思考、服务排队和输出速度。未观测到的字段保持缺省，历史记录不补造指标。

当前九次专业调用、八层依赖是编排基线。本次优化尚未完成真实模型的端到端对照测速，以下历史十八次调用及实跑时间均属于旧编排，不代表优化后的实测表现。

Codex JSONL 只提取线程身份和生命周期，最终交付读取 `--output-last-message` 文件；Grok 解析实际 JSON 包装与结构化结果。素材发现专用 Grok 调用改用 streaming-json，实际网页工具事件写入每个 run 的 discovery-evidence.json；available_commands 只证明已提供，必须另有真实工具调用才能采用检索结果。没有网页调用的占位结果最多恢复一次，每个实际 CLI 进程有独立 runId、目录及开始/失败/完成事件；保持 web 权限，不套用普通研究的禁网交付纠正。两次仍未执行则明确失败，不保存成功会话映射。原始工具输出、stderr 和私有推理不进入公开对话。进程超时、非零退出、缺少完成事件、无效 JSON 或阶段校验失败均不会发布为已完成成果。
